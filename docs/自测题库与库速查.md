## Part B：12 个最容易"读过去但没真懂"的细节

1. **`os.environ.setdefault`**（env_loader.py）：`.env` 只在环境变量不存在时写入 → 所以"真实环境变量 > .env"，
   测试才能在 import 前强制把引擎切到临时 SQLite。
2. **import 即副作用**：`db_api.py` 在模块导入时就 `load_dotenv()` + 建 `engine`，
   所以"谁先 import、环境变量什么时候设置"会决定连哪个库。
3. **`URL.create()` 做转义**：密码含 `@`、`#` 也不会拼坏连接串；SQLAlchemy 打印 URL 时自动把密码显示成 `***`。
4. **`String(255)` 的长度**：SQLite 不在意，MySQL 的 VARCHAR 必须给长度，否则建表报错——这是切库时最典型的坑。
5. **`pool_pre_ping` / `pool_recycle=3600`**：解决"连接被 MySQL 的 `wait_timeout` 掐断后拿到死连接"的问题。
6. **bcrypt 的 72 字节上限**：超长直接拒绝（避免静默截断）；`verify_password` 捕获异常返回 False（避免非法哈希导致 500）。
7. **JWT 的 `type` 字段**：access 与 refresh 不能混用；`decode_token(token, "access")` 会拒绝 refresh token。
8. **`_principal_from_token` 每次回库查用户**：token 里的 role/department 只是"签发时的快照"，
   真正生效的是数据库里的最新值——用户被禁用或调岗立即生效。
9. **`require_permission()` 是闭包工厂**：`Depends(require_permission("kb:read"))` 每个请求都会执行一次；
   403 在依赖层抛出，再被 `http_exception_handler` 包装成统一错误信封。
10. **`tenant_conditions()` 用 `*` 展开**：admin/system 返回空列表 → 相当于不加过滤；普通用户返回 `[department_id == X]`。
11. **Celery 的 `acks_late` + `visibility_timeout`**：前者保证"执行完才确认"，后者决定 worker 崩溃后多久重新投递（默认 1 小时，我们改成 300 秒）。
12. **幂等靠什么**：ES 的 `_id` 是确定性拼出来的（`doc_{document_id}_page_{n}`），所以任务重跑是"覆盖"而不是"写两份"；
    任务投递的幂等则靠 `find_active_task()`（有 pending/started 就复用）。

## Part C：自测题（20 道，闭卷作答）

### 功能 1：MySQL 双引擎

1. 为什么连接串必须写成 `mysql+pymysql://`？只写 `mysql://` 会发生什么？
# 发生连接错误，没有pymysql驱动
> **批改 ✅ 对。** 补充：`mysql+pymysql` 是"方言 + 驱动"的写法，少了 `+pymysql`，SQLAlchemy 找不到底层 DBAPI，
> 在 `create_engine()` 阶段就会报错（No module named 'pymysql' / 方言加载失败），根本还没到连接数据库那一步。
2. `.env`、`config.yaml`、真实环境变量三者同时存在时，谁的优先级最高？这个特性在测试里怎么被利用？
# 真实环境最高，.env次之，测试也要懂吗，测试主要靠.yaml
> **批改 ⚠️ 前半对、后半反了。** 优先级你答对了：真实环境变量 > `.env` > `config.yaml`。
> 但测试**恰恰不靠 yaml**：`test/conftest.py` 在 import `db_api` 之前，用**真实环境变量**把引擎强制切到临时 SQLite，
> 利用的正是"真实环境变量优先级最高"这条规则。如果测试靠 yaml（里面写的是 mysql），跑一次 pytest 就连上开发库了。
3. 迁移脚本 `migrate_sqlite_to_mysql.py` 为什么要显式保留原主键 ID？不保留会导致什么具体故障？
# 因为之前已经有数据建表了，不保留，之前数据会乱
> **批改 ⚠️ 方向对，但没说透。** 准确原因：ES 里的分块/摘要用 `document_id` / `knowledge_id` 与数据库记录关联，
> 删除、检索、评测全都依赖这组 ID。**不保留 ID，MySQL 里的 ID 就和 ES 里的 ID 对不上**——
> 元数据指向文档 A、向量却属于文档 B，删除时删错、检索时召回到别的文档（幽灵数据）。
> 另外脚本还做了 `AUTO_INCREMENT = max(id)+1`，否则新插入的记录可能复用老 ID，再和 ES 撞车。

### 功能 2：Alembic

4. `Base.metadata.create_all()` 和 Alembic 的本质区别是什么？各适合什么场景？
# 前者字段在建表时确定，不能增加或删除字段这些，后者可以更新版本，可以增加字段
> **批改 ✅ 基本对。** 说得更准确一点：`create_all` 是"表不存在就建，表已存在就**完全跳过**"，
> 所以它**永远不会 ALTER**；Alembic 把每次结构变更固化成版本脚本，可 upgrade / downgrade、多环境一致。
> 场景：`create_all` 适合临时脚本或一次性测试；任何要长期维护、要上线的项目都用 Alembic。
5. 三命令用途辨析：`alembic upgrade head`、`alembic stamp head`、`alembic downgrade -1`。
# 第一个可以在当前已经有表和数据情况，把当前表作为第一个版本，第二个更新版本，适合在没有数据和表，建表使用，
> **批改 ❌ 这两个说反了（这是最容易混的点，务必记牢）。**
> - `upgrade head`：**真正执行迁移脚本**，把库从当前版本升到最新（建表 / 改表）——不是"标记版本"；
> - `stamp head`：**不执行任何 SQL**，只写 `alembic_version` 表，把版本"标记"为 head——存量库已经建好表时用它；
> - `downgrade -1`：**回滚**最近一次迁移，执行该迁移里的 `downgrade()` SQL。
> 一句话：**upgrade 干实事，stamp 只盖章，downgrade 是后悔药。**
6. 为什么这次重构之后的启动流程里，"先跑 alembic upgrade head"变成了必需的一步？
# 因为当前项目已经有表了
> **批改 ⚠️ 不准确。** 真正原因：我们在 `db_api.py` 里删掉了 `Base.metadata.create_all(engine)`，
> 程序启动时**不再自动建表**。所以新环境 / 新库必须先用 `alembic upgrade head` 把表建出来，
> 否则启动后第一次查询就会报表不存在。存量库（你的 rag 库）当时是用 `stamp head` 标记的，不用重建。

### 功能 3：JWT 认证

7. bcrypt 和"直接 md5 密码"的区别是什么？为什么不能明文存储？
# 前者哈希和加密生成，后者不知道，因为这样子容易泄露密码，遭到攻击
> **批改 ⚠️ 一半对。** 关键差异在**成本和盐**：
> - bcrypt 是**单向哈希**（不是加密，无法反解）+ **每个密码随机盐**（同样的密码存进去结果不同，防彩虹表）
>   + **可调计算成本**（故意算得慢，暴力破解代价极高）；
> - MD5 是快速哈希，无盐/固定盐，GPU 每秒能算几十亿次，早被证明不适合存密码；
> - 明文存储：数据库一旦泄露（拖库），所有用户密码直接暴露；用户又常常复用密码，会连累他在别的网站上的账号。
> 补充：bcrypt 只取前 72 字节，所以代码里对超长密码做了拦截。
8. access token 与 refresh token 分开设计的目的是什么？`type` 字段防的是什么？
# 目的为了更好保护用户信息，防的是别人拿token来尝试攻击
> **批改 ⚠️ 太笼统，面试需要更具体。** 分开的核心是**暴露面与有效期**：
> - access token 有效期短（30 分钟）但要随每次请求发送，泄露了也只有 30 分钟窗口；
> - refresh token 有效期长（7 天）但只在换新 token 时使用（放到请求体里），不必每次请求都暴露；
> - `type` 字段防的是**token 混用**：refresh token 不能直接调业务接口（否则等于一张 7 天有效的通行证），
>   access token 也不能拿去刷新。代码里 `decode_token(token, "access")` 就是这个校验，并且有测试覆盖。
9. 登录失败时为什么统一返回"用户名或密码错误"？这样做的安全收益是什么？
# 为什么让那些黑客不知道具体错误，可以更好保护用户
> **批改 ✅ 对。** 专业名词叫**防用户名枚举（username enumeration）**：
> 如果提示"用户不存在"，攻击者就能批量试探出哪些用户名是有效的，再针对性撞库。统一提示让两种失败无法区分。

### 功能 4：RBAC + 多租户

10. 401、403、404 在这个项目里分别代表什么场景？（各举一个真实接口例子）
# 不清楚，忘记了
> **批改 ❌ 这题是重点，补上：**
> - **401 未认证**：没带 token / token 过期或签名不对。例：不带 Authorization 调 `GET /v1/knowledge_base/list`；
> - **403 无权限**：身份有效但角色没这个能力。例：viewer 调 `POST /v1/knowledge_base`（缺 `kb:write`）；
> - **404 看不见**：有权限，但数据不在你的可见范围（或真不存在）。例：viewer 读别的部门的 `GET /v1/knowledge_base?knowledge_id=N`。
> 记忆法：**401 不知道你是谁，403 知道你是谁但不许干，404 你有权限但这条数据你看不到。**
11. 跨部门查询为什么返回 404 而不是 403？换成 403 会带来什么风险？
# 忘记了
> **批改 ❌ 补上：** 返回 404 是为了**不泄露资源是否存在**。如果返回 403，攻击者就能拿 ID 一个个试
> （1、2、3…），通过"403 还是 404"判断哪些 ID 真实存在，从而摸清别的部门有多少知识库、ID 是多少——
> 这叫**资源枚举 / IDOR 探测**。让"无权访问"和"不存在"返回完全一样，攻击者就拿不到任何信息。
12. 请求体里传 `department_id=99` 为什么无效？服务端的归属是从哪里取的？
# 忘记了
> **批改 ❌ 补上：** 因为 `KnowledgeRequest` 里已经**删掉了** `owner_id` / `department_id` 字段，
> 你传了也会被 Pydantic 忽略（不报错但不生效）。真正的归属由服务端决定：从 JWT 解出 user_id，
> 用 `_principal_from_token()` **回数据库查当前用户**，再在 `add_knowledge_base()` 里写入
> `owner_id=principal.user_id`、`department_id=principal.department_id`。**客户端永远不能决定数据归属。**
13. 只在 MySQL 查询里加 `department_id` 过滤够不够？为什么 ES 检索也要加？
# 不够，ES检索不加会检索其他部门的数据，造成混乱
> **批改 ✅ 对。** 措辞可以更重一点：这不是"混乱"，是**数据泄露**——
> 检索入口是 ES 的 chunk，不加过滤就会把别的部门的分块召回到你的 Prompt 里，越权拿到别部门的内容。
> 所以租户隔离必须**在所有数据出口都做**：MySQL 查询一套、ES 检索一套（`rag_api.py` 里 BM25 和 KNN 各一处）。

### 功能 5：Celery 异步

14. 为什么任务函数只接收 `document_id`，而不是把 title/file_path 一起传过来？
# 这样子简短，只需要知道ID就可以获取其他相关字段了
> **批改 ✅ 对，但有两个更重要的理由：**
> ① 避免**过期快照**——worker 真正执行时以数据库里的最新值为准（任务排队期间文档可能被改名/删除）；
> ② Celery 消息只传可 JSON 序列化的标量，参数越少越安全、越可预期（重试时参数不变）。
15. worker 执行到一半被强杀（关窗口），任务会经历哪些状态？多久会被重新投递？由哪个配置决定？
# 任务会一直停在pedding,直到过期，然后自动改为start，由visibility_timeout决定
> **批改 ⚠️ 一半对。** 修正细节：
> - 任务**不是停在 pending**：worker 领取任务时会先 `mark_started`，所以数据库里停在 **started**；
> - 消息在 Redis 里处于 **unacked**（未确认）状态；
> - `visibility_timeout` 到期后（我们配了 300 秒；Celery 默认 3600 秒 = 1 小时）消息被**重新投递**，
>   任务**重新执行**（不是"把状态改成 start"）；重投时 `mark_started` 会把 started_dt 保留、状态仍为 started；
> - 这也解释了你之前遇到的"任务卡住不动"：默认 1 小时才重投，所以看起来像死了。
16. 同一个文档被重复投递两次，会不会在 ES 里产生重复分块？为什么？
# 不会，因为id一样的话，会覆盖，不会重新生成一遍
> **批改 ✅ 对。** 术语补充：ES 的 `_id` 是**确定性拼出来的**（`doc_{document_id}_page_{n}` / `..._chunk_{k}`），
> 所以重复写入是 **upsert（覆盖）**。这就是"任务可以安全重投"的底层保证——幂等。
17. `extract_content` 内部 `@with_retry(3)` 与 Celery 层 `max_retries=2` 叠加，最坏执行几次？为什么要设成有界的？
# 9次，有界不知道
> **批改 ⚠️ 数字对，"有界"要会解释。**
> - Celery `max_retries=2` = 首次 + 2 次重试 = 任务最多跑 **3 次**；
> - 每次任务内部 `with_retry(3)` = 最多 **3 次**尝试；
> - 最坏 3 × 3 = **9 次**。
> "有界"的意义：重试次数的乘积是**有限常数**，不会无限重试。如果 ES 挂了而任务无限重试，
> 会把 CPU/连接/日志全打满（雪崩）。所以重试必须配两样东西：**上限** + **退避**（我们用了指数退避），
> 而且任务本身必须**幂等**，否则重试会制造重复数据。

### 功能 6：测试与清理

18. 测试为什么必须用临时 SQLite？如果不做隔离，跑一次 `pytest` 会发生什么？
# 因为之前没有MYSQL就使用了，现在不好改
> **批改 ❌ 理解偏了，真正原因跟"以前有没有 MySQL"无关：**
> 测试会**写和删数据**——`test_permission.py` 的 teardown 会 `DELETE` 知识库表和文档表。
> 不做隔离的话，你跑一次 `pytest` 就会把 **MySQL 开发库里的真实数据清空**。
> 用临时 SQLite 是让每次测试都从零开始、跑完自动删除，互不影响。**即使项目只用 MySQL，也应该用独立的测试库。**
19. CI 为什么用 `requirements-ci.txt` 而不是 `requirements.txt`？`RAG_SKIP_INTEGRATION=1` 解决了什么问题？
# 不知道
> **批改 ❌ 补上：**
> - `requirements-ci.txt` 只装测试需要的**轻量依赖**，不装 torch / transformers（约 2GB），CI 启动快、省资源；
> - `RAG_SKIP_INTEGRATION=1` 会让 `test/conftest.py` 的 `collect_ignore` **跳过 8 个重型测试文件**
>   （它们 import `rag_api` 就会拉 torch，而且需要 ES / 模型 / Ollama，CI 里跑不了）；
> - 所以 CI 跑的是"秒级单元测试"，重型集成测试留在本地手动跑。
20. 旧的文件版状态机（`TaskStateMachine`）为什么可以删？删掉之后"任务状态"由谁负责？
# 忘记了
> **批改 ❌ 补上：** 因为任务状态已经由 **MySQL 的 `task` 表**负责（`task_store.py` 读写，`/v1/task` 接口查询，
> worker 在每个阶段 `mark_started / mark_success / mark_failure`）。旧状态机把状态写到 SQLite 的 `task_state` 表，
> 功能重复且没人查询，属于**死代码**；两套状态并存还有"双写不一致"的风险，所以删掉。
> 删除影响面很小：只动了 rag_api 里的 4 处 `set_state`、main.py 的 reset 调用和一个测试文件。

## Part E：自评等级（对每个功能给自己打分）

| 等级 | 标准 |
|---|---|
| L1 能背 | 知道这个功能叫什么、用了什么库 |
| L2 能解释 | 能说清"解决什么问题、为什么这么设计" |
| L3 能改 | 能独立加一个字段/改一个配置/加一个接口 |
| L4 能排错 | 出故障时知道先看哪、怎么定位、怎么恢复 |

**面试至少要到 L3，最好有一个功能到 L4。** 比如 Celery：你亲手处理过 `unacked` 卡住 + 重投，
这就是 L4 的经历，一定要在心里过一遍"当时怎么判断、怎么恢复"，面试官很吃这套。
