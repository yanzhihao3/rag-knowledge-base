# 图片内容 OCR 入库方案

> 场景：**面向开发者的技术文档问答助手**
> 目标：让"代码怎么写""参数怎么对比"这类问题，也能被检索到并答出来。

---

## 一、场景：先定需求，再定技术

### 1.1 场景定义

> 用户上传技术书籍 / API 文档 / 开发手册，用自然语言提问，系统返回**带出处的答案**；不仅回答概念，还能回答"**代码怎么写**"和"**参数怎么对比**"。

| 维度 | 内容 |
|---|---|
| 用户 | 正在使用某技术栈的开发者 |
| 输入 | 技术 PDF（书籍、手册、官方文档） |
| 输出 | 带出处的答案（章节 + 页码） |
| 典型使用 | 边写代码边查："这个功能怎么实现""这两个类有什么区别" |

### 1.2 用户会问什么（场景决定的三类问题）

| 类型 | 例子 | 答案载体 | 你现在能答吗 |
|---|---|---|---|
| **实操题** | "LangChain 里怎么用 NLTK 做文本切分？" | **代码** | ❌ 不能 |
| **对比题** | "LangChain 支持哪些特殊格式的切块？" | **表格** | ❌ 不能 |
| **概念题** | "什么是混合检索？" | 正文 | ✅ 能 |

### 1.3 从场景推出"要做什么"

```
场景：开发者查技术问题
        ↓
他们要的是"能抄的代码"和"能对比的参数表"
        ↓
但这两类内容在 PDF 里全是【图片】，文本层一个字都没有（实测）
        ↓
所以要 OCR —— 这就是本方案的由来
```

**一句话：不是"因为图片有意思所以做"，是"场景要求的内容恰好是图片，所以必须 OCR"。**

### 1.4 边界：这个场景下暂时不做什么

| 不做 | 场景理由 | 技术理由 |
|---|---|---|
| 架构图/流程图的图意描述 | 开发者很少问"这张图说明了什么"，他们问"怎么实现" | 需要 VLM（花钱），本项目保持 0 成本 |
| 公式 | 技术文档里公式不是主流问题 | OCR 出来是乱码（`RMS(a)=√∑i=1"a²`） |
| 封面/扉页 | 无问答价值 | — |

> 这两条**明确写进文档**——把边界说清楚，比含糊地"没做"强。

## 二、借鉴了哪些项目（每一处设计对应谁）

### 2.1 对照表

| 借鉴的项目 | 它的做法 | 我抄哪一条 | 落到本方案哪一步 |
|---|---|---|---|
| **Elastic 官方 RAG 架构** | ES 做检索层：BM25 + 向量 + RRF | 检索层设计 | **不用改**——现有双路召回 + RRF 已与它同构 |
| **RAGFlow** | 版面分析 + OCR + 表格识别，**表格单独成块**，召回时与正文一起给 LLM | ① 表格独立成块 ② 块里带表题 | 阶段 1（表格块） |
| **LlamaIndex `MarkdownElementNodeParser`** | 表格抽成独立 node，并生成**表格摘要**用于检索；原表保留用于生成 | "摘要块 + 原表块"双记录 | 阶段 4（可选增强） |
| **Anthropic Contextual Retrieval** | 每块入库前**补一段上下文**（LLM 生成），显著提升召回 | **块文本 = 标题 + 引用句 + 内容** | **阶段 1、2 的核心做法**（见 2.2） |
| **厂商文档助手**（AWS / GitHub Copilot Chat 文档模式） | 答案**必带出处**，可点击跳原文 | 引用溯源 | 阶段 3 |
| **Dify** | 知识库分块模式化（通用 / 父子 / Q&A） | 父子分段用在"表格摘要 → 原表" | 阶段 4 |

### 2.2 重点：我们做的是 Anthropic Contextual Retrieval 的"免 LLM 版"

Anthropic 的做法：**每个块入库前让 LLM 写一句"这段出自哪里、在讲什么"，拼在块前面**。召回率提升明显，但每个块都要调一次 LLM，成本高。

我们的做法：**用 PDF 里现成的标题和引用句代替 LLM 生成**。

```
Anthropic：  [LLM 生成的上下文] + 块内容
我们：       【小节标题】+【正文引用句】+ 块内容
             ↑ 都是 PDF 里现成的，零成本
```

**依据是实测的分词数据**（不是拍脑袋）：

```
表题「表4-1 LangChain提供的特殊文本切块方法」→ langchain, 特殊, 文本, 切块, 方法
问句「LangChain支持哪些特殊文本切块方法」  → langchain, 支持, 哪些, 特殊, 文本, 切块, 方法
                                              ↑ 高度重合 → BM25 稳稳命中

而表格内容本身「| 文本格式 | 类名 | Python代码 | PythonCodeTextSplitter |」
                                           → 与问句只重叠 python / 代码 / 文本
```

**结论：孤立的内容检索不到，必须带语义锚点。这是本方案最重要的一条设计。**

### 2.3 我们和借鉴对象的差异（面试可讲）

| 维度 | 企业级做法 | 我们 | 为什么 |
|---|---|---|---|
| 解析 | 商业 API 或自研版面模型（MinerU / RAGFlow deepdoc，3-5GB + GPU） | 本地 RapidOCR（200MB，纯 CPU） | 成本；且本书正文有文本层，只有图片需要 OCR |
| 上下文增强 | LLM 生成上下文前缀 | 用现成的标题 / 引用句 | 零成本，且技术文档天然有标题结构 |
| 检索 | 混合检索 + RRF + rerank | **一致** | 已实现 |

## 四、方案设计

### 4.1 整体流程

```
PDF
 │
 ├─① 定位与分类（三条规则，不用人看）
 │     表格：正文"表X-Y"引用 → 表题页+后一页 → OCR 结构确认
 │     代码：形状 + OCR 特征（单列 + 含 import/def/self. 等）
 │     其余：丢弃
 │
 ├─② OCR（RapidOCR，本地 CPU，0 元）
 │
 ├─③ 拼块文本 = 【标题】+【引用句】+【内容】   ← 借鉴 Anthropic 思路
 │
 ├─④ 写 ES（新增 chunk_type / heading_path / source_page 字段）
 │
 └─⑤ 检索：不用改；生成：微调 Prompt 拼装
```

### 4.2 分类规则

| 判断 | 规则 |
|---|---|
| 表格 | 多列行（≥2 个文本块）占比 ≥ 50% |
| 代码 | 单列，且（含 `import `/`def `/`self.`/`print(`/`return ` **或** 代码符号 ≥8 个） |
| 公式 | 单列，含数学符号 ≥3 且代码符号 <5 |
| 架构图 | 文本块 ≤8，或平均字长 ≤8 |

**表格优先用"表号反查"定位（最可靠），OCR 只做确认。**

### 4.3 块文本拼装（决定能不能被检索到）

| 块类型 | 块文本 = | 标题 / 引用句从哪来 |
|---|---|---|
| **表格块** | `【表题】表4-1 xxx` + `【正文】具体如表4-1所示。` + `【表格】` + Markdown | 正文正则取 `表X-Y 标题` 和含"如表X所示"的句子 |
| **代码块** | `【小节】4.2.2 xxx` + `【正文】代码如下所示。` + `【代码】` + 代码 | 正文取 `\d+(\.\d+)+\s` 标题行 + 含"代码如下"的句子 |
| （可选）图片块 | `【图注】图4-3 xxx` + `【正文】如图4-3所示。` + OCR 标注词 | 同表格 |

### 4.4 ES 字段与 id

```python
'chunk_type':   {'type': 'keyword'},   # code / table / figure / text
'heading_path': {'type': 'text', 'analyzer': 'ik_max_word'},
'source_page':  {'type': 'integer'},
'image_ref':    {'type': 'keyword'},
```

id：`doc_{document_id}_img_{page}_{idx}`（与现有块区分，互不覆盖）
兼容：现有 628 条不动；新字段用 `put_mapping` 加，不用重建索引。

### 4.5 检索侧

| 环节 | 改动 |
|---|---|
| BM25 / kNN / RRF / rerank | ❌ 不用改（新块的 `chunk_content` 就是文本） |
| 生成端 `_format_related_document` | ⚠️ 微调：表格加"以下是一张表格"，代码用 ``` 包裹 |
| （配套）标识符分词 | 加 `word_delimiter_graph` sub-field——否则搜 `TextSplitter` 匹配不上 `PythonCodeTextSplitter` |

### 5.2 阶段 2a：简单第一步 —— 上下文引用定位

**思路**：不靠形状/符号猜，靠**书自己说的话**定位。正文里凡是有
`代码如下所示` / `示例代码` / `测试代码如下` / `如下代码` / `以下代码` / `上述代码` / `代码实现`
的地方，它附近的图**大概率是代码**——这是高置信度信号。

**实测数据**：

| 指标 | 数值 |
|---|---|
| 含代码引用的页 | **35 页** |
| 引用句所在页 + 后一页的图（排除已入库的表格图） | **80 张** |
| 占全书图片 | 32% |
| OCR 耗时 | 约 9 分钟（80 张 × 6.6 秒） |

**做法**：
```
① 正则找引用句所在的页
② 取该页 + 后一页的图（排除已是表格的）
③ OCR → 用下面的分类规则确认
④ 拼块文本 = 【小节标题】+【引用句】+【代码】
⑤ 入库，id = doc_{did}_code_{page}_{idx}
```

**块文本示例**（目标形态）：
```
【小节】4.2.2 基于NLTK的文本切分
【正文】LangChain也集成了用NLTK进行文本切分的方法，代码如下所示。
【代码】
from langchain.text_splitter import NLTKTextSplitter
text_splitter = NLTKTextSplitter()
docs = text_splitter.split_text(text)
```

### 5.3 阶段 2b：分类规则（已调试出来的版本，早上直接用）

判定顺序**很重要**（顺序错了会互相抢）：

```
① 表格？        → 复用 build_table_chunks._is_table
② 代码关键词？   → import / def  / class  / self. / print( / return / () /
                   #include / console.log / function  / async  / await
③ 代码语句模式？ → 正则 [A-Za-z_]\w*\s*=\s*[^=] 或 [A-Za-z_]\w*\([^)]*\)
                   且"注释外的中文" ≤ 2
④ 符号密度？     → =(){}[]:;_ 占比 > 10%，且"注释外的中文" ≤ 2
⑤ 公式？        → 数学符号（∑√∫±×÷^）≥3 且中文 <3
⑥ 架构图？       → 文本块 ≤8 行，或平均字长 ≤8
⑦ 其他
```

**关键概念：`_cjk_outside_comment`（注释外的汉字数）**
这是三轮调试后得出的核心判据：

- **真代码**截图里的中文只出现在 `#` 注释行（如 `#不同的模型，我们需要调整这些参数`）
- **示意图/流程图**的中文是独立标签（如 `输人 输出 w(t-2) w(t-1)…`）

所以不能用"含中文就排除"，要看**中文是不是只在注释里**。

**三轮踩坑记录**（别重复踩）：

| 轮次 | 问题 | 修法 |
|---|---|---|
| 1 | 示意图 `输人 输出 w(t-2)…` 被判成代码 | 符号密度判断加"中文要少" |
| 2 | 带中文注释的真代码 `config = LoraConfig(...) #不同的模型…` 被漏判 | 改成"**注释外**中文要少" |
| 3 | 单行代码 `dataset = load_dataset("csv",…)` 被"架构图"规则抢走 | 加"代码语句模式"判断，且排在架构图之前 |

**分类器脚本**：`scripts/classify_code_images.py`（支持 `--sample N --seed X` 抽样验证）

**抽样验证结果**（seed=3, 20 张）：`{'代码': 17, '其他': 3}`，人工核对未发现误判。

### 5.5 第三路召回（2026-09-21 完成）

**为什么加**：代码块放同一个池子里比 BM25 会被正文块压死 ——
正文块一页 600-800 字、词频高；代码块大半是符号、中文匹配词少。
结果是用户问"代码怎么写"，召回的全是**描述代码的正文**，拿不到代码本身。

**怎么加**：在原有双路之外再加一路，只查 `chunk_type ∈ {code, table}`。

```
改前：BM25(全部) ──┐
                    ├─ RRF ─→ top10 ─→ rerank ─→ top5
      向量(全部) ──┘

改后：BM25(全部)      ──┐
      向量(全部)      ──┼─ RRF ─→ top10 ─→ rerank ─→ top5
      BM25+向量(仅代码/表格) ──┘
```

代码位置：`rag_api.py` 的 `RAG._typed_search()` + `query_document()` 的并行段与 RRF 段。
**原有两路一行没改**，只是多一路，所以回归安全。

**效果**：

| 测试 | 加之前 | 加之后 |
|---|---|---|
| 代码类问题（6 道） | 3/6 | **5/6** |
| 表格类问题（2 道） | 2/2 | 2/2 |
| **50 题概念题回归** | MRR 0.883 / 仅子块 90% | **MRR 0.903 / 仅子块 92%** |

概念题不但没被挤掉，还涨了 —— 新入库的表格块本身也能回答部分概念题。

**已知遗留**：`LoraConfig` 那张代码图（第213页图1）仍被判成非代码。
它的中文注释在**行内**（`config = LoraConfig(...) #不同的模型`），虽然已经按 `#` 截断处理，
但仍未通过 —— 需要单独看一眼（可能是 OCR 把注释和代码分到了不同行）。

### 5.7 标识符分词（2026-09-21 完成）

**要解决的问题**（实测）：

```
代码里的 PythonCodeTextSplitter  → IK 切成 ['pythoncodetextsplitter']   ← 一个整体
用户搜 TextSplitter              → 切成 ['textsplitter']
                                   两者不相等 → 搜不到
```

也就是说用户**必须打全名**才搜得到，而真实场景里没人记得住完整类名
（"那个 TextSplitter 有哪些？"是常见问法）。

**做法**：给 `chunk_content` 加一个子字段 `delim`，挂自定义分析器：

```json
"code_identifier": {
  "type": "custom",
  "tokenizer": "standard",
  "filter": ["word_delimiter_graph", "lowercase"]
}
```

效果：`PythonCodeTextSplitter` → `python` / `code` / `text` / `splitter`

**两个踩坑点（都实测过）**：

1. **tokenizer 必须是 `standard`，不能用 `ik_max_word`** —— IK 会先把英文转小写，
   `word_delimiter_graph` 就看不到驼峰边界了。实测 ik 版依然是
   `['pythoncodetextsplitter']`，standard 版才拆得开。
2. **filter 顺序不能反** —— 必须 `[word_delimiter_graph, lowercase]`（先拆后转小写）。

**代价与对策**：`standard` 会把中文切成单字（`混合检索` → `混/合/检/索`）。
所以**查询侧只把英文标识符送到这个字段**（`_identifier_clauses()` 用正则从查询里
提取长度 ≥4 的英文词），中文查询仍走主字段 —— 否则中文查询会命中一堆无关文档。

**另两个踩坑**：

- 加 sub-field **不会自动回填老文档**，必须让它们重写一遍。`update_by_query` 默认
  `detect_noop=true`，脚本没变化就跳过；而 `detect_noop` **不是合法的 URL 参数**。
  最终用"给所有文档打 `schema_version = 2`"强制重写（711 条一次到位，秒级）。
- 重新索引后 HNSW 图会重建，**向量路的结果可能有 1 道题的轻微波动**（近似检索的正常现象）。

**效果**：

| 查询 | 改之前 | 改之后 |
|---|---|---|
| "TextSplitter 有哪些"（半截类名） | ❌ 搜不到 | ✅ 前 3 条全是代码块 |
| "ParentDocumentRetriever 怎么用"（全名） | ✅ | ✅ |
| "混合检索是怎么做的"（纯中文） | ✅ | ✅ 未受噪音影响 |
| **50 题回归** | MRR 0.903 | **MRR 0.903（持平）**，关键词 98%→100%，答案页 96%→98% |

脚本：`scripts/add_identifier_tokenizer.py`（幂等，新环境建完索引后跑一次即可）；
`es_api.py` 的 mapping 已同步，新建索引会自带这个分析器。

查询侧：`rag_api.py` 的 `_identifier_clauses()`，被 `_word_search` 和 `_typed_search` 使用
（用 `should` + `minimum_should_match: 1`，两个字段命中任一即可）。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| OCR 噪声（公式 / 图表混入） | 分类规则过滤 + 低置信度丢弃 |
| 代码符号错误（`l`/`1`、下划线） | 检索影响小（关键词仍命中）；生成影响可选二次校正 |
| 跨页表格（表4-1 跨 108/109） | 按表号合并，取起始页 |
| 解析时间 58 秒 → 8-10 分钟 | Celery time_limit 要调 + 进度上报 |
| 幂等重灌 | 确定性 id + 按 document_id 先清（复用现有机制） |
